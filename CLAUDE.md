# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

No git repo, no build step, no linter. Two source files matter: `light_bounces.py` (the whole app, ~8.6k lines) and `test_light_bounces.py` (+ `test_harness.py`).

```bash
python -m py_compile light_bounces.py      # compile-check
python test_light_bounces.py               # full suite (~8s); custom runner, not pytest
python light_bounces.py                    # launch the Tkinter app
```

- There is no single-test CLI flag. Tests are plain `test_*` functions (no args, raise `AssertionError`) discovered from module globals by `run_all()`. To run one: `python -c "import test_light_bounces as t; t.test_name()"`.
- Requirements: `numpy`, `numba` (without it everything runs in pure Python, unusably slow), `ffmpeg-python` + the `ffmpeg` binary for video, optionally `cjxl` for JPEG XL output.
- Baseline (verified on Windows, 2026-09-29): all 419 pass, none fail or skip, provided `cjxl` and `ffmpeg` are on PATH. Without the real `cjxl`/`ffmpeg`, `test_convert_apng_to_jxl_with_the_real_cjxl_produces_a_jxl_file` reports SKIP (not PASS); everything else still passes.
- cjxl tests are hermetic: `_PathContext` (in the test file) strips any real `cjxl` from PATH, then either leaves none (`_no_cjxl()`) or puts `dev/testing/` first (`_fake_cjxl(fail_on=...)`). The fakes there (`cjxl.cmd` for Windows, `cjxl` for POSIX) copy input to output, or fail if the input path contains `$FAKE_CJXL_FAIL_ON`. Keep the two fakes behaviorally identical.
- `convert_apng_to_jxl` runs the path from `shutil.which("cjxl")`, not the bare name, because on Windows a bare name won't launch `.cmd`/`.bat` shims.
- Source files use CRLF line endings, except `dev/testing/cjxl` (the POSIX fake), which must stay LF or its `#!/bin/bash` line breaks. When editing from a Python script, read and write in binary mode (or `newline=''`) so line endings aren't silently changed.
- Numba caches compiled kernels in `__pycache__` (`cache=True`); first run after editing a kernel is slow.

## Architecture

**Single-file Tkinter app.** `light_bounces.py` shoots a ray from every pixel inside any shape ("obstacle") whose "fire rays inside" is on. There is no separate bounding shape: the app starts with one obstacle (`default_starting_obstacle`: the unit circle, Reflect both ways, fires rays). At each shape edge a ray reflects, terminates or passes through, chosen separately for crossing in and crossing out; it also reflects off its own earlier path, and escapes if nothing is left to hit. Per-ray measurements are stored per pixel, so recoloring is instant without re-simulating. The module docstring (top of file) is the authoritative feature description; read it first.

Layout of the file, in order:
1. Constants/parameters, "Buddha" (density-scatter) blur kernels.
2. Data classes: `Keyframe`, `Obstacle`, `ViewConfig`, `Snapshot`/`Settings` (only the stopping limits, segment multiplier, fuzzing and Buddha blur - the scene itself is obstacles and views), plus `SETTING_INFO`/`DEFAULT_SETTING_VALUES`/`SETTING_FLOAT_KEYS`/`SHAPE_PARAM_INFO`/`OBST_FIELD_INFO` registries.
3. Pure helpers: keyframe interpolation (`resolve_frame_settings`, `resolve_value`, `resolve_obstacle_arrays`, `resolve_views`), filename/settings text, parsers, hand-written PNG/QOI/JXL encoders and PNG decoder, image utils.
4. Geometry: shapes are built by `make_bound(shape, params)` into packed arrays (arcs+edges, or circles) that numba kernels can consume.
5. Coloration tables/metric catalogs, then `run_self_checks()` (called at import).
6. Numba kernels: `arcs_edges_hit`/`circles_*_hit` → `boundary_hit` (ray inside a shape) / `obstacle_hit` (ray outside it) → `trace_path` (one ray; every shape is an obstacle, passed as the parallel arrays from `build_obstacle_arrays`) → `compute_stats`/`compute_points` → `render_rows(_wh)` and `scatter_multi_buddha` (parallel, row-banded).
7. `class App` (~4.4k lines, lines ~4200–8580): all UI, generation threads, timeline/keyframes, video render (`_render_worker`, `encode_video_output`).

Key design points that span multiple places:
- **Keyframes snapshot everything** needed to generate an image, independent of the live controls. Float settings are interpolated *linearly* between keyframes; non-numeric settings hold the earlier value. There are no per-keyframe interpolation methods and no keyframe thumbnails (both removed ahead of a planned keyframe overhaul; `Keyframe` is just `id`, `frame_index`, `data`). The obstacle-list and view-list thumbnails (`THUMB_SIZE`) are unrelated and stay. Dynamic lists (obstacles, views) use keys like `"obst:<id>:<field>"` / `"view:<id>:..."` so each list item's fields animate independently and list position never matters. Deleting an obstacle or view immediately purges its keys from every keyframe (`purge_keyframe_settings`); a render works from `snapshot_keyframes` copies so such edits can't leak into it.
- **Parallel registries must stay in sync**, and `run_self_checks()` enforces this at import time (e.g. `SETTING_INFO` vs `DEFAULT_SETTING_VALUES`, `Obstacle.__slots__` vs `OBST_FIELD_INFO`, `SHAPE_PARAM_INFO` field/widget uniqueness, per-`TERM_*` dicts, point-catalog lengths). When adding a setting, shape param, termination code, or metric, update every table; a self-check failure at import is the intended alarm. Tests deliberately break a fresh module copy to confirm each check fires.
- **Ray effects** (`OBSTACLE_EFFECT_REFLECT/TERMINATE/PASS`): `trace_path` tracks which shapes the ray is inside with a flag per shape, flipped by each pass-through crossing and never re-derived from geometry (except after a segment-multiplier pull-back). A crossing is not a bounce, records no point, and is part of one segment (`total_t`). A shape passing rays through both ways is skipped. `TERM_ESCAPED` rays end where they leave the [-1, 1] square (`square_exit_t`). Termination-reason metric values are evenly spaced 0..1 (`TERM_STAT_VALUE`); a new reason means rescaling them.
- **Angle controls are unlimited where the angle is a free quantity:** emission offset, fuzzing offsets, every obstacle rotation and theta take any number of degrees (`add_angle_entry` with no `lo`/`hi`), while a fuzzing jitter (a +/- range) keeps its 0-180 limits. The shape-defining angles keep the limits their geometry needs (Moss egg apex angle 60-180, circular sector span up to 180, circular segment span 1-359; `moss_egg_bound`/`make_bound` clamp them too).
- **Confinement** is a figure-defining setting (Simulation tab, `build_confinement_controls`): window size (2-999 path points), method (`CONFINE_BOX`: the window's bounding box is under the threshold in BOTH directions; `CONFINE_PATH`: the window's segments sum to under it) and one threshold in world units (any finite number > 0, never rounded or clamped - `parse_confine_threshold`; the key-press check is `validate_positive_float`). Defaults (4, Box, `PIXEL` = 2/512) are exactly the old hard-wired rule, guarded by the golden test. It reaches the kernels as the `confine` array (`confine_array` / `settings_confine` / `CONFINE_DEFAULT`), right after `fuzz`. Keyframes: threshold interpolates, window and method hold. The rule is judged on the *recorded* path points, so with a segment multiplier below 1 those are the pulled-back points. Not built (declined): circle-radius detection, periodic-orbit detection. Note `TERM_CONFINED` is also (mis)used for a degenerate zero-length normal and the pass-through crossing safety cap; splitting them out would need a new termination reason (which re-spaces the termination metric).
- **Emission direction** is a figure-defining setting (Simulation tab, `build_emission_controls`): mode `EMIT_UP` (base direction 90 degrees) or `EMIT_TOWARDS` (from each ray's own start point to the target point; a ray starting exactly on it uses up), a target point positioned like an obstacle - four settings `emit_target_r` / `_theta` (degrees) / `_cx` / `_cy` (`EMIT_TARGET_FIELDS`; the point is `obstacle_center_from(r, theta, cx, cy)`, computed in `settings_emission`, so the kernels still receive x and y), each any finite number, `parse_target_coordinate`, never clamped, and an angle offset in degrees (positive = counterclockwise, *no limits* - any number of revolutions either way) ADDED to the base. Defaults (Up, target origin, offset -45) reproduce the old fixed up-and-right direction *bit-for-bit*: `unit_direction` returns exact vectors at multiples of 45 degrees. It reaches the kernels as the `emission` array (`emission_array` / `settings_emission` / `EMISSION_DEFAULT`), right after `confine`. The offset applies in Towards mode too, so aiming exactly at the target needs offset 0. Fuzzing's old absolute "emission angle" was REMOVED (it replaced the direction whenever fuzzing was on, which would have defeated Towards); `FuzzParams` and the kernel's `fuzz` array now have only `emit_jitter`, added on top of the emission direction (so `fuzz` has 8 entries, indices shifted). The ray preview follows the *generated* image's settings until Start is pressed again.
- **Testing the kernels:** `dev/testing/classic_boundary_golden.npz` is recorded output of the *old* fixed-bounding-shape implementation (ten scenes: every shape kind, plus fuzzing/segment-multiplier/distance-limit); `test_a_figure_obstacle_reproduces_the_recorded_classic_golden_data` checks that an ordinary obstacle still reproduces it, so keep it. Compiled kernels use their own RNG: seed it from compiled code (`_seed_kernel_rng`), not `np.random.seed`. Test scenes must start rays *inside* a firing shape (`_kernel_trace` puts a unit-circle figure first), or the ray correctly bounces off that shape's outside.
- **Terminology - "figure" vs "image":** the *figure* is the mathematical result of perfectly simulating the rules (like the Mandelbrot set); it can never be generated whole, and every picture the program makes is an *image* (a view) of it. What defines the figure: the stopping limits, segment multiplier, fuzzing and the obstacles. Coloration, decorations and the Buddha blur only process or decorate generated data and are NOT part of it. Never call an obstacle or an exported picture "the figure" (the export choices are "Current image" / "New image"; the code says `render_current_image`, `has_image`).
- **Figure settings margin:** the Export designer's "Figure settings location: Left margin" writes every figure-defining setting (`figure_info_blocks`: limits, segment, fuzzing, and each obstacle via `obstacle_info_lines`) using lines of at most `FIGURE_INFO_COLUMN_CHARS`. The margin is half the image width, growing extra text columns when needed; its size depends only on the image size and the obstacle count (blocks have fixed heights), so all frames of a video match. Video frames resolve obstacle values per frame (`resolve_obstacles`).
- **Pixel font (`FONT_5X7`):** complete for A-Z, a-z, 0-9 plus `#`, theta and a few symbols (each glyph is 7 rows of 5 cells; `render_text_line` looks characters up strictly, so a missing one raises KeyError). The user has said new characters may be added to it whenever useful, without asking - add the glyph and a test. Known long-standing look-alikes: `o`/`0` and `x`/`\u00d7` share a picture.
- **Point dropdowns:** "Origin" and "Top left corner" are listed first (`POINT_MENU_LABELS`), but point ids never change (`POINT_LABELS.index(label)` still maps a label to its id).
- **Selecting a keyframe loads it; edits are marked "modified"** (`select_keyframe`, `apply_keyframe_settings`, `check_modified`): selecting loads every setting the keyframe defines plus every one its neighbors animate through it (`setting_status` "animated" = some other keyframe defines it, on either side: blended between the nearest on each side, or held from the first/last defining keyframe when only one side has one - `resolve_value`'s rules; settings no keyframe defines are left alone). Selecting another keyframe = deselecting first (`deselect_keyframe`: clicking the empty keyframe-list background, deleting the selected one, or selecting another); the controls keep their values but `kf_modified` is cleared. Modification is detected by *polling* `capture_all_settings` every `MODIFIED_POLL_MS` (`poll_modified`; ~0.06 ms per capture) and diffing against the previous capture (`detect_modified_keys`): any change marks a key, and it stays marked even if typed back, until saved or deselected. New keys (a just-added obstacle) are not edits; vanished keys are dropped. `kf_applying` suppresses checks while values are loaded. Blue outlines are `ModifiedOutline` frames placed behind each control (no layout changes), found via `SETTING_WIDGET_ATTRS` / `OBSTACLE_FIELD_WIDGET_ATTRS` / `SHAPE_PARAM_INFO` (self-checks keep these in step with `SETTING_INFO` / `OBST_FIELD_INFO`; a new setting needs its control attribute registered) and `chan_blocks` / `mode_combo` for views; obstacle and view outlines show only for the obstacle/view currently open in the editor. "Save all modified" (`save_modified_settings`) and per-setting Save clear those marks; there is no per-setting Load and no Load all. `new_keyframe` (from current) does not reload; `new_keyframe_empty` does.
- **Keyframe settings list sections are collapsible** (Timeline panel, `refresh_timeline_diffs`): each header (`diff_section_header_text`) toggles via `toggle_diff_section`; `App.diff_expanded` holds the expanded titles (empty = all collapsed by default, kept across rebuilds and keyframe selection). Every rebuild ends with `fit_diff_scroll` (the scroll area can't rely on the list frame's `<Configure>`: when the list shrinks below the scroll position the canvas shows none of it and never sends one, leaving a blank list). Collapsed sections build no rows, but Load all / Save all / Delete all still act on every setting. Obstacle/view sections are keyed by their "Obstacle #N" / "View N" title, so expansion follows list position. A "Show" filter above it (`diff_presence_var`: present / absent / present or absent, default all) narrows the rows via `setting_passes_presence_filter`; sections with no match are hidden, and the bulk buttons ignore the filter.
- **Pinned previews:** a pinned pixel keeps tracing its ray even where nothing fires (`update_preview`), and clicking it always unpins it (`on_click`); hovering a non-firing pixel shows nothing.
- **All output goes to `exports/`** (`EXPORT_DIR`, created on demand via `ensure_export_dir()`); video frames go in `exports/TEMP/` (`TEMP_DIR`). Tests must patch `m.EXPORT_DIR` / `m.TEMP_DIR` to a temp dir so nothing lands in the real folder.
- **The window is kept on screen at startup** (`keep_window_on_screen`, run 100 ms after the UI is built and again just before the startup screenshot): it only moves the window (never resizes it) by the smallest `shift_into_area` amount so its whole frame lies in the work area of its monitor (taskbar excluded; Windows asks the OS via ctypes in `window_rect_and_work_area`, other platforms use the client rectangle and whole screen). A window bigger than the screen is lined up by its top-left corner. The window is ~1920 px wide including its frame, so on a 1920-px screen only vertical moves show.
- **Debug aids (dev aids; all need the `dev/` folder, and never raise):** the Debug menu (`build_menu_bar`: Take screenshot / Dump (without large arrays) / Dump (with large arrays)) and, once per launch shortly after startup (`take_startup_captures`, scheduled at the end of `warm_up`), a screenshot then a dump. Screenshots go to `dev/screenshots/<FILE_VERSION>-YYYYMMDD-hhmmss-<startup|manual>.png` (Pillow's `ImageGrab`, real screen pixels, so anything covering the window appears; skipped without Pillow). Dumps go to `dev/dumps/<FILE_VERSION>-YYYYMMDD-hhmmss-<startup|crash|manual>.pkl` (`dump_app_state`; a same-second name gets `-2`, `-3`... via `unused_path`). Startup and crash dumps, and "Dump (without large arrays)" ones, replace every numpy array of at least 64 KiB (`LARGE_ARRAY_BYTES` in the dumper; purely by size, wherever it sits - the generated `stats`/`points`/`img`..., the `gx`/`gy` pixel grids, the hover buffers - so there is no list of attributes to maintain) with a stand-in recording its shape, dtype and size: a dump is then ~0.1 MB instead of ~52 MB. Crashes (an exception escaping a Tk callback via `on_callback_exception`, reaching `sys.excepthook`, or killing a thread) dump at most `MAX_CRASH_DUMPS` per launch, and never take a screenshot. The dumping itself lives only in `dev/debug_dump.py` (standalone; loaded by path at dump time): it knows nothing about the app's attributes, stores whatever pickles exactly as is, and replaces the rest with plain-dict stand-ins marked `__standin__` (Tk variables keep their value, widgets their options, unpicklable objects their attributes). Read a dump with `debug_dump.load_dump(path)`, which maps classes pickled as `__main__` (the program run as a script) to `light_bounces`. `dev/dumps/` is gitignored. Tests patch `m.DEV_DIR` (and `m.ImageGrab`) to a scratch dir.
- **The program never deletes files on its own.** The one exception is the Video panel's Clear button (`clear_temp_frames`), which, after confirmation, deletes only `frame_NNNNN.png` from `TEMP_DIR`. A video render refuses to start if `TEMP_DIR` is non-empty or two keyframes share a frame index.
- Output filenames derive from the script's own filename, so renaming the file changes them.

## Testing

`test_harness.load_module()` stubs `tkinter`/`ttk`/dialogs with no-op widgets so the real module imports headlessly and its plain functions/classes can be tested. Each call returns a fresh module object (use it for tests that mutate module state). Anything needing a live Tk mainloop is out of scope and checked by hand. Bug fixes get a regression test whose docstring says what went wrong.

## Working preferences for this project

- After every edit: compile-check, then run the full test suite, not just
  tests that seem related.
- Flag risk and disagree with a plan when warranted, rather than silently
  complying or silently deviating. If a request has an unintended side
  effect, say so and explain the tradeoff before proceeding.
- Keep a visible, incrementing version counter in a long-lived file,
  updated on every delivery. This is `FILE_VERSION` near the top of
  `light_bounces.py`: bump it by exactly 1 once per
  completed task/turn that changed the file, not per individual edit.
