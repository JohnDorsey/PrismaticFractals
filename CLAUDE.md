# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

There is a git repo (the user commits between turns), no build step, no linter. The app is the package `lightbounces/` (started by the launcher `light_bounces.py`; the project is not a single file - see the module map and the numba caching constraint under Architecture); its tests are in `tests/` (run by `test_light_bounces.py`; the headless loader is `test_harness.py`).

```bash
python -m compileall -q lightbounces tests light_bounces.py test_light_bounces.py test_harness.py   # compile-check (silent when fine)
python test_light_bounces.py               # full suite (~15 s); custom runner, not pytest
python light_bounces.py                    # launch the Tkinter app
```

- Tests are plain `test_*` functions (no args, raise `AssertionError`) in `tests/test_<area>.py` (areas: coloration, colorations, debug, dump_viewer, export, framings, images, inputs, kernels, package, preview, projects, selfchecks, settings, shapes, timeline, video, widgets); helpers, fake apps and fixtures used by more than one area are in `tests/support.py`, which also holds the one loaded copy of the package, `m`, and `ROOT` (the project folder). `tests/runner.py` finds them by name (sorted, so the order does not depend on the file): `python test_light_bounces.py kernels colorations` runs areas, `-k golden` runs tests whose name contains the text, `--list` lists the areas. Put a new test in the area of what it tests; a helper used by a second area moves to `support.py`. A name must be unique across all files.
- Requirements: `numpy`, `numba` (without it everything runs in pure Python, unusably slow), `ffmpeg-python` + the `ffmpeg` binary for video, optionally `cjxl` for JPEG XL output.
- Baseline (verified on Windows, 2026-10-07): all 736 pass, none fail or skip, provided `cjxl` and `ffmpeg` are on PATH. Without the real `cjxl`/`ffmpeg`, `test_convert_apng_to_jxl_with_the_real_cjxl_produces_a_jxl_file` reports SKIP (not PASS); everything else still passes.
- cjxl tests are hermetic: `_PathContext` (in `tests/test_video.py`) strips any real `cjxl` from PATH, then either leaves none (`_no_cjxl()`) or puts `dev/testing/` first (`_fake_cjxl(fail_on=...)`). The fakes there (`cjxl.cmd` for Windows, `cjxl` for POSIX) copy input to output, or fail if the input path contains `$FAKE_CJXL_FAIL_ON`. Keep the two fakes behaviorally identical.
- `convert_apng_to_jxl` runs the path from `shutil.which("cjxl")`, not the bare name, because on Windows a bare name won't launch `.cmd`/`.bat` shims.
- Line endings: the working files are CRLF (Windows; git stores LF, `core.autocrlf=true`) - every `.py`, `.md`, `.cmd` and `.gitignore`. Exceptions that stay LF: `dev/testing/cjxl` (the POSIX fake; its `#!/bin/bash` line breaks with CRLF; `.gitattributes` pins it to LF) and the `.lightbounce` project files (the program writes them with LF). The Edit tool preserves a file's endings; from a Python script read and write in binary mode and keep `
`. The dev tools in `dev/refactor/` write LF into new modules: convert new files to CRLF afterwards.
- Numba caches compiled kernels in `__pycache__` (`cache=True`); first run after editing a kernel is slow. **numba only checks the modification time of the file a kernel is defined in, so a kernel keeps running stale code when a *constant* it reads, or another `@njit` function it calls, is changed in a *different* file (verified twice with small modules: `python dev/refactor/numba_cache_check.py`; the result stayed the old value until the kernel's own file was touched).** So `lightbounces/kernels.py` defines every `@njit` function that calls another, every constant a kernel reads (and whole numbered families such as `TERM_*`, `SHAPE_*`, `ST_*`) and the kernel argument types, and imports nothing from the package except `njit`/`prange` (from `external.py`); the QOI encoder in `image_io.py` calls no other kernel and reads only `np`, so it stays there. `test_the_numba_kernels_read_only_names_defined_in_their_own_file` enforces this for every file of the package (checker: `dev/refactor/kernel_reads.py`, also runnable as a script). Put a new kernel constant in `kernels.py`, never in another module. Measured after the split (`python dev/refactor/kernel_cost.py`, first kernel calls): warm 3.9-4.0 s; after touching any other file still 3.9-4.0 s (before the split, touching the one big file cost 6.4 s); after touching `kernels.py` 6.3 s once.

## Architecture

**Tkinter app** (the `lightbounces` package; `light_bounces.py` is only the launcher, and the module docstring that describes the features is the docstring of `lightbounces/__init__.py`). The program shoots a ray from every pixel inside any shape ("obstacle") whose "fire rays inside" is on. There is no separate bounding shape: the app starts with one obstacle (`default_starting_obstacle`: the unit circle, Reflect both ways, fires rays). At each shape edge a ray reflects, terminates or passes through, chosen separately for crossing in and crossing out; it also reflects off its own earlier path, and escapes if nothing is left to hit. Per-ray measurements are stored per pixel, so recoloring is instant without re-simulating. The module docstring (top of file) is the authoritative feature description; read it first.

Module map of `lightbounces/` (bottom-up: a module imports only from modules above it in this list; `__init__.py` imports them all, re-exports every name of every module so `lightbounces.write_png` works wherever it lives, and then runs `selfchecks.run_self_checks()`):
1. `version.py` (FILE_VERSION), `paths.py` (folders, PROGRAM_NAME), `external.py` (optional ffmpeg / Pillow / numba as attributes), `widgets.py` (outline, tooltip, scrollable tab...), `image_io.py` (PNG/QOI/JXL encoders, PNG decoder, pixel font, text drawing, resizing).
2. `kernels.py`: every numba kernel (`arcs_edges_hit`/`circles_*_hit` → `boundary_hit` / `obstacle_hit` → `trace_path` (ended by the shared `is_confined` / `beyond_escape_radius`) → `compute_run_measurements` (the ray's own run measurements) and `compute_sequences` (over `sequence_summary` and `in_sequence`: the reductions of the named sequences) → `trace_rows` (over the parallel `_trace_rows_parallel`) and `scatter_from_seeds` / `scatter_multi_buddha`), every constant they read (`PREVIEW_BOX`, `DEFAULT_PIXEL_WORLD_WIDTH`, `TERM_*`, `SHAPE_*`, `EMIT_*`, `CONFINE_*`, `EPS`..., `KIND_*`, `OBSTACLE_EFFECT_*`, `ST_*`/`N_STATS`, `POINT_*`/`N_POINTS`, `SEQ_*`/`PRED_*`/`SRED_*` with the `POINT_SLOT`/`STAT_SLOT` tables, `RAW_*`/`N_RAW`, `OBST_OBJ_BASE`) and the kernel-argument namedtuples (`FuzzRule`, `ConfineRule`, `EmissionRule`, `ObstacleArrays`, `WorldRect` (the world rectangle an image covers), and the two bundles `NaturalTerminationRule` and `RayArgs`). Nothing else may define a kernel constant.
3. `constants.py` (ranges, defaults, UI colours and sizes - nothing a kernel reads), `settings.py` (strict records, `RaySettings`, `NaturalTerminationSettings`, `BuddhaBlurSettings`, the spec tables, `Keyframe`, `resolve_*`, rule builders), `geometry.py` (the bound builders and probes; the packed layouts are described in its docstring), `shapes.py` (`Shape` and its 12 subclasses, `make_bound`, ring layers, thumbnails, `build_obstacle_arrays`), `metrics.py` (the named-sequence catalogs and the metric/point/Buddha choices generated from them, the blur functions, `make_mapping`), `colorations.py` (`ColorationConfig`, snapshots, `ChannelSettings`, `resolve_colorations`, colour models), `framings.py` (`FramingConfig`, `FramingSnapshot`, a framing's world rectangle, image size, outline pixel and margin text), `export_text.py` (option lists, file names, coloration/figure info text and drawing), `projects.py` (catalogs, `Project`, JSON, migrations), `parsing.py`, `window.py`, `debug.py` (`dump_app_state`, a patchable global read as `debug.dump_app_state`), `ui_text.py`, `selfchecks.py`.
4. The window: `class App` in `core.py` (only `__init__` and `main()`) is assembled from 14 mixins, one module each, whose methods use `self.x` and the attributes `__init__` creates: `app_projects`, `app_export`, `app_framing`, `app_render`, `app_video`, `app_timeline`, `app_debug`, `app_generation`, `app_preview`, `app_recolor`, `app_obstacles`, `app_coloration`, `app_controls`, `app_layout`.
Dev tools in `dev/refactor/`: `numba_cache_check.py` (demonstrates the stale-kernel fact), `kernel_cost.py` (first-kernel-call timing: warm ~4 s, cold ~6.5 s, unchanged by edits outside `kernels.py`), `kernel_reads.py` (the checker behind the kernel-rule test), `project_roundtrip_check.py` (real-window save/New/Open/Start check; run it after changing project, window or generation code), `undefined_names.py` (names a function uses but its module does not define - run it after moving code, tests do not call every method), `extract_tool.py` / `extract_methods.py` / `prune_imports.py` (move definitions or methods between modules).

Key design points that span multiple places:
- **Keyframes snapshot everything** needed to generate an image, independent of the live controls. Float settings are interpolated *linearly* between keyframes; non-numeric settings hold the earlier value. There are no per-keyframe interpolation methods and no keyframe thumbnails (both removed ahead of a planned keyframe overhaul; `Keyframe` is just `id`, `frame_index`, `data`). The obstacle-list and coloration-list thumbnails (`THUMB_SIZE`) are unrelated and stay. Dynamic lists (obstacles, colorations, framings) use keys like `"obst:<id>:<field>"` / `"coloration:<id>:..."` / `"framing:<id>:<field>"` so each list item's fields animate independently and list position never matters. Deleting an obstacle, coloration or framing immediately purges its keys from every keyframe (`purge_keyframe_settings`); a render works from `snapshot_keyframes` copies so such edits can't leak into it.
- **Records of settings are strict dataclasses** (`strict_record`): `FuzzParams`, `BuddhaBlurSettings`, `RaySettings` (the ray-bouncing engine's own settings: segment length multiplier, fuzzing, emission), `NaturalTerminationSettings` (the limits that end ANY sequence of points: `max_iter`, `max_dist`, `escape_radius` and the three confinement settings - what the Termination tab's "Termination limits" and "Confinement" sections hold), `KeyframeData` (`.ray`, `.natural_termination`, `.buddha_blur`, `.outline`), `ColorationSettings`, `ColorationSnapshot`. They are frozen, `slots`, **keyword-only with every argument required** (no defaults, so a new field must be passed everywhere and a missing one is a TypeError), cannot be indexed, iterated or unpacked, and check every value against its annotation (int / float (an int is fine, a bool is not) / bool / str / tuple (a list is stored as a tuple) / a class) - so a type mistake fails at construction, naming the record and field. `r.replace(**changes)` makes a modified copy, `r.as_dict()` a shallow dict, and they pickle by field name (`__getstate__`; dataclass's own state for frozen slotted classes is a bare positional list). `ColorationSnapshot` is a frozen copy of one live `ColorationConfig`, for the background threads (new-image export, video render); its fields mirror the live class's `__slots__` (a test keeps them in step). An obstacle's frozen copy is a frozen `Shape` instead (see the obstacle paragraph). Attach a validator before `@dataclass` runs, or it is never called (`strict_record` does). `settings_of_current_image` gives the settings the image on screen was generated with - colorations are colored from those (Buddha coloration re-traces rays with the generated `gen_termination` and `gen_engine_args` tuples). **Neither the Buddha blur nor the natural termination limits are part of `RaySettings`: `BuddhaBlurSettings` (radius, type) and `NaturalTerminationSettings` are records of their own, used side by side with it everywhere they are held** - `KeyframeData(ray, natural_termination, buddha_blur, outline)`, `Project.ray` / `Project.natural_termination` / `Project.buddha_blur`, `current_ray_settings()` / `current_natural_termination_settings()` / `current_blur_settings()` (and `current_generation_settings()` = `(ray, natural_termination)` or None, what Start, the button states, `capture_project` and `capture_all_settings` use), the export text (`settings_suffix(ray, natural_termination)`, `image_filename(ray, natural_termination, ...)`, `figure_info_blocks(ray, natural_termination, obstacles)`, `apply_info_locations(rgb, colorations, coloration_width, ray, natural_termination, obstacles, ...)`), and `apply_coloration(v, stats, characteristic_points, pixel_state, w, h, blur, termination, engine_args, rng_seed_base)` takes the blur as its own argument (`termination` - a `NaturalTerminationRule` -, `engine_args` - a `RayArgs` - and `rng_seed_base` are the engine's, used only to re-trace rays for the "multi" Buddha point options). **The blur is live:** it is not part of what an image was generated with (no `generated_blur`, not in Start's comparison or Revert's baseline); Buddha channels are always colored with `current_blur_settings()`, and a change (`on_buddha_blur_changed`, also called when a keyframe loads a blur) schedules one coalesced `refresh_blur`, which drops the cached blurred counts and non-live thumbnails and recolors from the stored counts - no Start. **One table row per setting, one table per settings record** (`NATURAL_TERMINATION_SETTING_SPECS` for `NaturalTerminationSettings`, `RAY_SETTING_SPECS` for `RaySettings`, `BLUR_SETTING_SPECS` for `BuddhaBlurSettings`; a `SettingSpec` each: the path into its record, the control attribute, the widget the modified-outline surrounds, and how the control is written - `text`/`int_text`/`float_text`/`number`/`bool`/`choice`). `SETTING_TABLES` (record class -> its table) is the one place that lists the records, `DEFAULT_SETTINGS` their defaults; `SETTING_SPECS` (all rows), `SETTING_INFO`, `SETTING_FLOAT_KEYS` (every float-typed field), `SETTING_WIDGET_ATTRS` and `DEFAULT_SETTING_VALUES` are *derived* from them. `settings_to_dict(*records)` / `settings_from_dict(record_class, values)` (used by `capture_all_settings`, `resolve_frame_settings` and the project code; int fields are rounded, bool fields made bool; setting keys are unique across all tables), `set_setting_control` (used by `load_value` and Revert, so there is one setter, not two). `run_self_checks` fails at import if a record field has no row (or a row has no field), so adding a setting means: the record's field, its default, a row in its table (which carries the label/tab), the control and its reading in `current_ray_settings`/`current_blur_settings`/`preview_settings`; a new KIND of settings (another way to generate bounces, say) is a record class, a table and an entry in `SETTING_TABLES`/`DEFAULT_SETTINGS`. Choice settings (`emit_mode`, `confine_method`, `buddha_blur_type`) also need an entry in `SETTING_CHOICE_CATALOGS` (their project-file keys) `preview_settings` (hover/pinned ray previews: the generated settings once an image exists, else the controls using each entry's last valid value - no blur: a ray preview does not need it) and `current_ray_settings` / `current_natural_termination_settings` (the controls' live parsed values, None while an entry is invalid; used through `current_generation_settings` by Start, the button states and keyframe capture) still build a `RaySettings` / `NaturalTerminationSettings` separately (`preview_natural_termination_settings` for previews). What the image on screen was generated with is `generated_settings` AND `generated_natural_termination` (both None until Start; `baseline` / `baseline_natural_termination` are what Revert restores; the kernel-ready tuples `gen_termination` and `gen_engine_args` - which holds the obstacles as generated - are made from them in `start`; `settings_of_current_image` / `natural_termination_of_current_image` give them or the defaults). A keyframe stores a coloration channel as a `ChannelSettings` record (`coloration_channel_value`), the keyframe settings list is built from `SettingEntry` records (`all_setting_entries`), and outlines from `ObstacleRing` records (`obstacle_ring_specs`); each setting's label and tab are in its spec row (`SETTING_INFO` is derived). **Kernel arguments are namedtuples, not records** (numba needs them, and cannot forbid indexing or positional construction): `FuzzRule`, `ConfineRule`, `EmissionRule` (built only by `fuzz_rule` / `confine_rule` / `emission_rule`), `ObstacleArrays` (shapes, bounds, cx, cy, effects, fire_inside; built only by `build_obstacle_arrays`, from live shapes or frozen copies alike) and the two bundles of the above that the kernels take: `NaturalTerminationRule(max_iter, max_dist, escape_radius, confine)` (built by `natural_termination_rule` / `settings_natural_termination` / `NATURAL_TERMINATION_DEFAULT`; `max_dist` is the kernel's, infinite for no limit) and `RayArgs(seg_mult, fuzz, emission, obstacles)` (built by `ray_args` / `settings_ray_args`; the fuzzing seed travels separately as `rng_seed_base`). In the kernels read them only as `rule.field` - a misspelled field is a compile error, and `test_kernels_read_their_rule_and_obstacle_arguments_by_field_name_never_by_number` scans the kernel sources for numeric indexing. (Verified: numba passes namedtuples through `prange` kernels and nested calls, caches them, and they are immutable inside kernels; a record *value* does not work inside `prange`, and a structured array still allows integer indexing.) The kernel signatures are `trace_path(x0, y0, path_points, path_point_tags, termination, engine_args, raw)`, `trace_rows(stats, characteristic_points, pixel_state, row0, row1, out_w, out_h, world_rect, termination, engine_args, rng_seed_base)` (`pixel_state` is a uint8 per pixel: `PIXEL_PENDING` 0 = its row is not rendered yet, `PIXEL_TRACED` 1 = a ray was fired and its stats and characteristic points stored, `PIXEL_NO_RAY` 2 = reached but outside every firing shape; a finished render leaves none pending; colouring reads only `PIXEL_TRACED`; the constants are in `kernels.py` as the kernel writes them) and `scatter_multi_buddha(row0, row1, world_rect, termination, engine_args, rng_seed_base, want..., counts)` (`world_rect` is a `WorldRect`). **numba limitation, verified (numba cannot compile it, with "'str' object has no attribute 'loc'"): a `parallel=True` function cannot use, inside its `prange` loop, a tuple that contains other tuples, nor take one as an argument and loop over it - but a parallel function that is given the ONE-LEVEL pieces can rebuild the whole tuples inside its loop.** So `trace_rows` is a plain `njit` wrapper that takes `termination` and `engine_args` whole and passes `termination.max_iter`, `termination.confine`, `engine_args.fuzz`, ... to `_trace_rows_parallel`, which build `NaturalTerminationRule(...)` and `RayArgs(...)` again for each pixel's `trace_path`; any other engine's parallel driver must do the same. Still positional: `Shape.params()` (a per-kind tuple, read only by the kind's `bound_from_params`), the registry row tuples (`ShapeParam`, `COLORATION_FIELD_INFO`, `SETTING_INFO`), the packed `bound[...]` shape layouts (documented in the docstring of `geometry.py` and above `ARC_FIELDS`; 39 index reads), and `effects[..., 0/1]` (incoming/outgoing).
- **Parallel registries must stay in sync**, and `run_self_checks()` enforces this at import time (e.g. `SETTING_INFO` vs `DEFAULT_SETTING_VALUES`, each shape kind's `__slots__` vs its parameter tables, `KIND` matching its place in `SHAPE_CLASSES`, a field name meaning the same on every kind, per-`TERM_*` dicts, point-catalog lengths). When adding a setting, shape param, termination code, or metric, update every table; a self-check failure at import is the intended alarm. Tests deliberately break a fresh module copy to confirm each check fires.
- **Ray effects** (`OBSTACLE_EFFECT_REFLECT/TERMINATE/PASS`): `trace_path` tracks which shapes the ray is inside with a flag per shape, flipped by each pass-through crossing and never re-derived from geometry (except after a segment-multiplier pull-back). A crossing is not a bounce, records no point, and is part of one segment (`total_t`). A shape passing rays through both ways is skipped. `TERM_ESCAPED` rays (nothing left ahead) end where they are `escape_radius` from the origin (`escape_exit_t`; a ray already that far out ends at once, and a ray never ends before the last edge it passed through) - the Termination tab's **Escape radius** (`RaySettings.escape_radius`, default 2.0, any finite number above 0, `parse_escape_radius`, keyframe-animated, project key `simulation.escape_radius`, listed in the figure-settings margin) replaced the old fixed [-1, 1] square, so an escaped ray's end point now lies outside the image at the default; it is also meant to be the Mandelbrot bailout radius when that generator exists. It is a field of the `NaturalTerminationRule` the kernels take (the test is `beyond_escape_radius`, shared with any other engine). Termination-reason metric values are evenly spaced 0..1 (`TERM_STAT_VALUE`); a new reason means rescaling them.
- **Named sequences (a coloration's channels choose any sequence's reductions; groundwork for swapping the engine):** a traced ray is ONE path of tagged points (`trace_path`'s `path_points` and `path_point_tags`); the engine declares named sequences that are filtered views of it, with `in_sequence(seq, k, kinds)` the one definition of membership, by a point's kind alone (every end point that is not a bounce has a kind of its own: `TAG_DISTCUT`, `TAG_OBSTACLE_TERM`, `TAG_ESCAPED`, `TAG_PERPENDICULAR` - a ray ended by exactly perpendicular incidence ends on one, and `nb` is not increased) - `SEQ_PATH` (every point, start to end; every engine should offer a sequence like it, "Path"), `SEQ_BOUNCES` (path_points[1..nb]: `TAG_BOUNDARY` or `TAG_SELF`), `SEQ_BOUNDARY` (TAG_BOUNDARY bounces), `SEQ_SELF` (TAG_SELF bounces). Every sequence is reduced, when the ray is traced, to the same stored numbers (PRECOMPUTED for all of them, so recolouring stays instant whatever a channel is given): seven points (`PRED_FIRST`/`LAST`/`MEAN`/`TOP`/`BOTTOM`/`RIGHT`/`LEFT`; an empty sequence reports the path's end point) and four scalars (`SRED_COUNT` points / iteration limit, `SRED_LENGTH` arctan-squashed polyline length, `SRED_LAST_DIR`; under two points the direction is 0.5, `SRED_SHARE` points / the path's bounces, 0 with none), all by `compute_sequences` -> `sequence_summary` (one pass per sequence). So `N_POINTS` = 4 x 7 = 28 and `N_STATS` = 24. **The old choices are ALIASES**: each `POINT_*` is one (sequence, reduction) (`POINT_ALIASES`; e.g. `POINT_SELF_TOP` = (`SEQ_SELF`, `PRED_TOP`)), `ST_BOUNCE_COUNT` / `ST_LENGTH` / `ST_LAST_DIR` / `ST_SELF_SHARE` / `ST_BOUNDARY_SHARE` are (`SEQ_BOUNCES`, count) / (`SEQ_PATH`, length) / (`SEQ_PATH`, last direction) / (`SEQ_SELF`, share) / (`SEQ_BOUNDARY`, share) (`STAT_ALIASES`); they keep their numbers as the FIRST slots of the stored arrays (`POINT_SLOT[seq, pred]` / `STAT_SLOT[seq, sred]` give every pair its slot, the rest following in order; `point_slot` / `stat_slot` in `metrics.py`), and the golden test compares only those first 13. The other eight metrics (the four point distances, loop area, bounce angles, termination reason, last-segment ratio) are measurements of the ray's own RUN, written by `compute_run_measurements` alone. **What a coloration can choose is GENERATED from these tables, not written out:** the Python side declares the sequences and reductions with labels, short names and descriptions (`SEQUENCE_LABELS`, `POINT_REDUCTION_LABELS`, `STAT_REDUCTION_LABELS`...), and from them `metrics.py` makes every choice's label, short name and description: each stored point is a point choice (`POINT_LABELS`: "Self bounces: Uppermost point"; 28, then the two fixed points `CHOICE_ORIGIN` = `N_POINTS` and `CHOICE_TOP_LEFT_CORNER`, which are choices with no slot), each stored metric a metric choice (`METRIC_LABELS`: only the eight measurements of the run in `RUN_METRIC_INFO` are written by hand, the others are "<sequence>: <reduction>"; `POINT_METRICS` are the four distances between two points, `OTHER_METRICS` the 20 others, in dropdown order), and the Buddha options (`BUDDHA_POINT_CATALOG`, 35: the 28 characteristic points, the path's last point for the rays a limit ended, and the four "multi" options; the Coloration tab shows them as a sequence x reduction grid of checkboxes with the other seven listed below). A choice's id is its stored slot, so the old `POINT_*` / `ST_*` numbers are unchanged. The ray preview lists all 24 metrics (`METRIC_SHORT`). `run_self_checks` keeps all of it in step (and every table must hold plain Python ints: numpy ones from the slot tables are refused by the strict `ChannelSettings`, regression test `test_every_metric_and_point_a_dropdown_can_choose_is_a_plain_int`). The two fraction metrics used to be measured from a separate count of edge hits (`RAW_BOUNDARY`, now removed) that also counted a final perpendicular hit which is no recorded bounce, so such a ray got -1 and 2; they are now ordinary shares of the Self and Boundary sequences for every ray (the one golden-data capsule ray that ends that way differs, so the golden test skips those two slots; `test_the_ray_fraction_metrics_are_the_shares_of_the_self_and_boundary_sequences_for_every_ray`). **Cost (measured):** the stored arrays are twice as big (320 bytes a pixel against 156: 80 MB against 39 MB at 512 x 512, and an export frame at 3840 x 2160 needs ~2.7 GB against ~1.3 GB, since `render_full_image` allocates them whole); the reductions add about 160 ns to a 6-point ray, 255 ns to a 20-point one and 1.7 us to a 200-point one (a render that takes ~0.15 s gets 5-15% slower; a render of long rays, where `trace_path` dominates, is unchanged within noise, 14.1-14.2 s against 14.1-14.7 s); results of the old 13 + 13 slots are bit-identical (pipeline hashes, the real window's image and all 15 recolours) except those two fractions on the few rays that end perpendicularly after a bounce (10 of ~70,000 across seven test scenes). Not done: the Buddha "multi" options as sequence x transform (they only use `in_sequence` for membership), and `in_sequence` / the reductions dispatching per engine, which a second engine needs before it can use them.
- **Sequence engines (groundwork for swapping the ray-bouncing engine for another producer of point sequences, e.g. an escape-time iteration):** what ends ANY sequence naturally is its own record and kernel tuple - `NaturalTerminationSettings` / `NaturalTerminationRule` (iteration limit `TERM_ITER`, distance limit `TERM_DIST`, escape radius `TERM_ESCAPED`, confinement `TERM_CONFINED`) - and the checks are shared kernels (`beyond_escape_radius`, `is_confined`) that `trace_path` itself calls; `test_another_engine_can_be_ended_by_the_same_natural_termination_rule_and_checks` runs a 15-line `z -> z^2 + c` orbit engine off them. What is still ray-specific and would have to be generalised for a second engine: `fires_ray` and the pixel -> start-point mapping with its fixed [-1, 1] world rectangle (kernels and the Python scatter code), the ray-only `ST_*` metrics, `KIND_*` point kinds, `RAW_*` slots and `TERM_OBSTACLE` / `TERM_PERPENDICULAR`, `seg_mult` inside `compute_run_measurements`, and the Python side's `RaySettings` / `current_ray_settings` / hover preview. Verified bit-identical by the pipeline hashes and the golden data, and no slower (interleaved old/new benchmark).
- **Obstacles are instances of `Shape` subclasses** (`EllipseShape`, `RegularPolygonShape`, `MossEggShape`, `CircularSectorShape`, `CircularSegmentShape`, `LensShape`, `ReuleauxPolygonShape`, `CapsuleShape`, the arc loops `TrefoilShape`, `QuatrefoilShape`, `LuneShape`, `ArbelosShape`, and the two squircles and the spiral ribbon `SuperellipseShape`, `FernandezGuastiShape`, `ArchimedeanSpiralShape`, `PythagorasSnailShape`, `HugelschafferEggShape`, `SineFlowerShape`; `SHAPE_CLASSES` is indexed by `KIND`, the `SHAPE_*` code the kernels use, and `SHAPE_NAMES` is derived from each class's `NAME`). The kind is chosen when the obstacle is created - the Obstacles tab's `new...` menu button, `new_obstacle(shape_class)` - and never changes: there is no `shape` field or control, so keyframes cannot change it, and an obstacle has only the fields its kind needs. `Shape` holds what every kind has (`rotation`, the position `r`/`theta`/`cx`/`cy`, `in_effect`, `out_effect`, `fire_inside`); each subclass declares its own parameters once, as a `PARAMS` tuple of `ShapeParam` rows (field, label, default, animate, fmt, slider range) plus `__slots__` with the same names (a self-check keeps the two in step), and a `LAYOUT` (how its bound array is packed: `LAYOUT_ELLIPSE` / `_POLYGON` / `_CIRCLES` / `_ARCS_EDGES` / `_ARC_LOOPS` / `_SQUIRCLE` / `_SPIRAL` / `_SNAIL` / `_EGG` / `_FLOWER`; the Python code that must treat packings differently, `offset_bound` and `ring_layer_masks`, branches on it, so a new kind that reuses a packing needs no edit there; the numba kernels `boundary_hit`, `obstacle_hit` and `inside_boundary` still branch on the kind's `KIND` code), and provides `params()` (the tuple its bound function takes), `bound_from_params`, `shape_text`, `extent`, `info_param_line` and, where the generic sampled edge is not exact, `boundary_xy`. `__init_subclass__` derives `NUMERIC_PARAMS`, `KEYFRAME_FIELDS` (field, label, is_float), `FIELD_NAMES` and `FIELD_TYPES`. A field type-checks on assignment (float: any real number but not a bool; int: whole numbers; bool: only a bool; an unknown field is an AttributeError). A *frozen copy* is the same class with every assignment refused: `snapshot()`, `with_values(**values)`; it is what the background threads read, what `gen_obstacle_snapshots` holds and what `resolve_obstacles` returns, and it has every method (describe, bound, center...). `duplicate(new_id)` makes a live copy of the same kind. Copy and pickle go through `__getstate__`/`__setstate__` (state `(None, {slot: value})`, what pickle gives any slotted object, so the dump viewer shows a shape as before). The editor builds one control group per kind from its `PARAMS` (`add_shape_param_row`, `obs_shape_groups`; `obs_widgets` is keyed `(Shape, field)` for a shared field and `(kind, field)` for a kind's own; read through `obstacle_widget`), shows the group of the selected obstacle's kind and its name (`obs_shape_label`). Keyframe keys are `obst:<id>:<field>` for the fields of that obstacle's own kind only, and its section of the keyframe list is titled by `obstacle_tab_title` ("Obstacle #2 (Lens)"). Every kind has the one `rotation` field but keeps its OWN zero orientation (polygon and Reuleaux vertex up, Moss egg pointed end up, ellipse width along x, sector/segment/lens/capsule along +x). `radius` is declared by polygon, Reuleaux, sector and segment (default `DEFAULT_RADIUS` = 1.0, range 0-2); polygon `sides` and `reuleaux_sides`, and the two spans, keep separate names on purpose (different ranges). Adding a kind: a subclass with `KIND`, `NAME`, `PARAMS`, `__slots__` and the methods above, its bound function and kernel support, a `SHAPE_*` code, a branch for it in those three kernels (unless a later change makes them dispatch on layout; the arc loops, kinds numbered `SHAPE_FIRST_ARC_LOOP` to `SHAPE_ARBELOS`, need none: `boundary_hit` and `obstacle_hit` fall through to `arcs_edges_hit`, and `inside_boundary` sends every code from `SHAPE_FIRST_ARC_LOOP` up to `inside_arcs_parity`, so a kind numbered after them (the squircles, the spiral, the snail, the egg and the flower are 12-17) needs its branch in `inside_boundary` placed BEFORE that range check), and an entry in `SHAPE_CLASSES` (the `new...` menu and everything else follow). A kind whose name is too long for the figure-settings margin's `Obstacle #N: NAME` line (`FIGURE_INFO_COLUMN_CHARS` = 32) gives a `SHORT_NAME` for it. The pixel font has `á` (for "Fernández-Guasti"). **The arc loops** are concave shapes built from full circles by `region_arcs(circles, member)`: it cuts each circle where it crosses the others and keeps the pieces where the region is on one side only (identical circles are one; a quatrefoil at lobe size 1 would otherwise count its edge four times and break the even-odd test). `lobed_bound` (trefoil/quatrefoil: `radius` is the distance to the farthest point, `lobe_size` the lobe radius as a fraction of it, 0.52-1; below 0.5 the middle would be a hole), `lune_bound` (the outer circle `radius` about the origin minus a circle `cut_radius` whose centre is `cut_offset` away towards the rotation; degenerate cuts give a full disc, a disc with a hole, or nothing), `arbelos_bound` (`radius` and `split`, centred vertically on its bounding box, curved side up at rotation 0). Their outline is `chain_arcs_xy` (arcs joined end to end; a lune with a hole draws a joining line) and their ring layers use `arc_loop_distance`, because offsetting a concave arc outward would move it into the shape. A concave shape does not change the crossing cap in `trace_path`: a shape passes rays one way only, so a ray is passed through any one shape at most once per segment.
  **The squircles and the spiral ribbon find their ray hits by root search along the ray, not in closed form** (`kernels.py`: `squircle_hit`, `spiral_hit`; both keep the `(t, normal)` contract of `boundary_hit` / `obstacle_hit`, so `trace_path` is untouched and scenes without them run bit-identically and as fast: measured with an interleaved old/new benchmark of a five-shape 512x512 scene, same output hash, no difference beyond +/-15% noise). Their bound is six numbers: area, cos and sin of the rotation (the shape is worked out in its own frame; points and directions are turned by minus the rotation, normals turned back), then the shape's three (layout described above `superellipse_bound`). **Squircles:** `squircle_f` is a function F that is below 0 inside, above 0 outside and CONVEX along every line (the superellipse's sum |x/a|^n + |y/b|^n - 1 for n >= 1; for Fernández-Guasti the square of the shape's gauge, (q + sqrt(q^2 - 4 s^2 x^2 y^2)) / (2 r^2) - 1 with q = x^2 + y^2, where the shape is x^2 + y^2 - (s^2/r^2) x^2 y^2 = r^2 with squareness s in [0, 1] and radius r, convex for every s - checked numerically). A convex F has at most two roots along a ray and Newton's method from the box-exit end (leaving) or the box-entry end (entering) creeps monotonically up on the root without overshooting, so it needs no bracket. The ray is first clipped to the shape's bounding box (semi-axes a, b; r, r). **The spiral ribbon** is the set of (rho, phi) with b*theta <= rho < b*theta + w for some theta in [0, theta_max] equal to phi plus whole turns (b = pitch / 2 pi, w = fill * pitch, theta_max = (radius - w) / b; radius under w gives an empty shape; `inside_spiral` is closed form). Its curved edges are the levels of D(t) = rho(t)/b - phi(t) along the ray (phi followed continuously): D = 2 pi k is the inner edge, D = 2 pi (k + fill) the outer one. D has exactly ONE turning point, in closed form (a quadratic in s^2), so the ray splits into a falling and a rising stretch; on each, the levels are crossed in order and each is solved by `spiral_solve` (bracketed Newton) and accepted if its theta is in range, so the usual cost is one or two solves. The two straight ends of the ribbon use `edge_exit_hit`. Verified against marching along random rays (24,000 rays over random parameters: the only disagreements were rays passing through the sub-pixel wedge where the ribbon starts at the centre, which marching cannot resolve). Per call: ellipse 28 ns, arc loop 130 ns, FG squircle 90-160 ns, spiral ~300 ns, superellipse ~470 ns leaving (several `pow` per Newton step). Their outline is exact (`squircle_outline_xy`, `spiral_outline_xy`) and their ring layers use first-order distances (`squircle_distance_grid`, `spiral_distance_grid` in `kernels.py`). **The snail of Pythagoras** (`PythagorasSnailShape`, `snail_segments` = a whole number of triangles, 1-100, default 17 - the first count whose last triangle overlaps the first turn; no size control: it is scaled so its farthest corner is 1 from the centre) is the UNION of n right triangles O, A_k, A_{k+1} (right angle at A_k, legs sqrt(k) and 1 before scaling), so it is star-shaped about O but not convex and, from 17 triangles on, O is inside it. Its bound is `[area, n, scale, A_1 .. A_{n+1} as x, y pairs]` with the rotation already applied (`snail_bound`; `OBST_BOUND_LEN` grew to hold 100 segments). A ray meets each triangle in one interval (`_snail_clip`, three half-planes), so `snail_hit` needs no root search: from outside the way in is the earliest interval start; from inside the way out is found by chaining the intervals that touch (`SNAIL_JOIN`), repeated until nothing extends it, the normal being that of the edge it leaves by. The two edges out from O count as INSIDE (a strict test left a one-pixel hole along every edge two triangles share, e.g. the 45 degree diagonal, which the default emission direction runs straight along; regression test). Cost grows with n: ~180 ns a call at 5 triangles, ~570 at 17, ~3.8 us at 100. Its outline is the farthest outer edge in each direction (`snail_outline_xy`, exact at the corners), its ring layers `snail_near_grid` (the nearest point of each close triangle edge, probed just either side, so edges the shape has on both sides are skipped). **The Hügelschäffer egg** (`HugelschafferEggShape`: `egg_a` half-length, `egg_b` half-width - exactly its widest half-width - and `egg_shift` = d / a in [-0.9, 0.9], clamped by `egg_bound`; the egg is closed for |d| < a; the pointed end is at +x for a positive shift) is, with u measured from the middle of its length, `y^2 (a^2 + d^2 + 2 d u) = b^2 (a^2 - u^2)`, |u| < a inside - the equation transcribed from mathcurve.com's page, `(x-d)^2/a^2 + y^2/b^2 (1 + (2dx - d^2)/a^2) = 1` with x = u + d (the page's parametrization, as transcribed, lacked a leading cos t: `x = cos t (sqrt(a^2 - d^2 sin^2 t) + d cos t)`, y = b sin t; checked against the equation). It is convex for every parameter (checked numerically) and has an infinite second branch outside |u| <= a. Its bound is `[area, cos, sin, a, b, d]` like the squircles; a ray's equation is a CUBIC in t, so `egg_hit` clips the ray to the box |u| <= a, |y| <= b (which excludes the other branch), finds the cubic's turning points (a quadratic) and takes the first root between them (`_cubic_root_in`, bracketed Newton) - the nearest crossing serves both `boundary_hit` and `obstacle_hit`. ~160 ns a call. Outline: the exact parametrization (`egg_outline_xy`); ring layers: first-order distance (`egg_distance_grid`, only within the ring width of the egg's box: further out the estimate goes to zero along the other branch's vertical asymptote, which at |shift| near 0.9 sits just past the egg's point and once drew a straight line across the image; regression test). Verified against marching along 24,000 random rays (no mismatches). **The sine flower** (`SineFlowerShape`: shared `radius` R, `flower_petals` k, a whole number 1-30, and `flower_amplitude` A, 0-0.95 so r stays positive) is rho < R (1 + A sin(k phi)) in its own frame, star-shaped about the centre but concave; area exactly pi R^2 (1 + A^2/2); bound `[area, cos, sin, R, A, k]`. A line at distance h from the centre has rho = h / cos(phi - phi0), so it meets the edge where g(phi) = h - r(phi) cos(phi - phi0) is 0 (g < 0 inside) - no division, and |g''| <= M = R (A k^2 + 2 A k + 1 + A). `flower_hit` searches only the stretch of the line between the inner and outer circles (one or two windows of phi, taken in the order the ray reaches them) and `_flower_window` skips an interval only when M PROVES it holds no root (g stays on one side of its tangent at either end), solving a sign change once |g'| beats M times the interval's length, halving otherwise - so a petal tip the line only grazes is still found. A line through the exact centre (h < 1e-9) is a separate radial case, because there rho = h / cos is 0 / 0 (without it every ray along the 45 degree diagonal from the diagonal pixels escaped from a closed flower; regression tests). The annulus is widened by 1e-7 so a circle (A = 0) still has a window. Cost is the highest of the new kinds: ~0.7 us a call with A = 0, ~1.8 us at 6 petals and A = 0.3, ~3.6 us at 12 petals and A = 0.6, ~9 us at 30 petals and A = 0.95; a 512x512 render at 500 iterations took 0.7-1.3 s. Outline exact (`flower_outline_xy`); ring layers (`flower_distance_grid`) slide each point along the gradient of rho - r(phi) four Newton steps and report the distance moved (the plain first-order estimate was badly wrong where the petals are steep). Verified against marching along 14,400 random rays (no mismatches). A square (squareness 1, or a 4-gon) fired at the default 45 degrees confines nearly every ray and renders slowly (~8-10 s at 512x512 x 500 iterations); that is the geometry, not the solver.
- **Angle controls are unlimited where the angle is a free quantity:** emission offset, fuzzing offsets, the obstacle rotation and theta take any number of degrees (`add_angle_entry` with no `lo`/`hi`), while a fuzzing jitter (a +/- range) keeps its 0-180 limits. The shape-defining angles keep the limits their geometry needs (Moss egg apex angle 60-180, circular sector span up to 180, circular segment span 1-359; `moss_egg_bound`/`make_bound` clamp them too).
- **Confinement** is a figure-defining setting (Termination tab, `build_confinement_controls`): lookback (2-999 path points: how many of the most recent ones are judged), method (`CONFINE_BOX`: the lookback's bounding box is under the threshold in BOTH directions; `CONFINE_PATH`: the lookback's segments sum to under it) and one threshold in world units (any finite number > 0, never rounded or clamped - `parse_confine_threshold`; the key-press check is `validate_positive_float`). Defaults (4, Box, `DEFAULT_PIXEL_WORLD_WIDTH` = 2/512) are exactly the old hard-wired rule, guarded by the golden test. It reaches the kernels as a `ConfineRule` namedtuple (`confine_rule` / `settings_confine` / `CONFINE_DEFAULT`), the `confine` field of the `NaturalTerminationRule`, and the kernels judge it with the shared `is_confined(path_points, npts, confine)` (so any engine producing a sequence of points can use it: for an orbit it is a convergence test). Keyframes: threshold interpolates, lookback and method hold. The rule is judged on the *recorded* path points, so with a segment multiplier below 1 those are the pulled-back points. Not built (declined): circle-radius detection, periodic-orbit detection. Note `TERM_CONFINED` is also (mis)used for a degenerate zero-length normal and the pass-through crossing safety cap; splitting them out would need a new termination reason (which re-spaces the termination metric).
- **Emission direction** is a figure-defining setting (Emissions tab, `build_emission_controls`): mode `EMIT_UP` (base direction 90 degrees) or `EMIT_TOWARDS` (from each ray's own start point to the target point; a ray starting exactly on it uses up), a target point positioned like an obstacle - four settings `emit_target_r` / `_theta` (degrees) / `_cx` / `_cy` (`EMIT_TARGET_FIELDS`; the point is `obstacle_center_from(r, theta, cx, cy)`, computed in `settings_emission`, so the kernels still receive x and y), each any finite number, `parse_target_coordinate`, never clamped, and an angle offset in degrees (positive = counterclockwise, *no limits* - any number of revolutions either way) ADDED to the base. Defaults (Up, target origin, offset -45) reproduce the old fixed up-and-right direction *bit-for-bit*: `unit_direction` returns exact vectors at multiples of 45 degrees. It reaches the kernels as an `EmissionRule` namedtuple (`emission_rule` / `settings_emission` / `EMISSION_DEFAULT`), the `emission` field of the `RayArgs`. The offset applies in Towards mode too, so aiming exactly at the target needs offset 0. Fuzzing's old absolute "emission angle" was REMOVED (it replaced the direction whenever fuzzing was on, which would have defeated Towards); `FuzzParams` and the kernel's `FuzzRule` now have only `emit_jitter`, added on top of the emission direction. The ray preview follows the *generated* image's settings until Start is pressed again.
- **Testing the kernels:** `dev/testing/classic_boundary_golden.npz` is recorded output of the *old* fixed-bounding-shape implementation (ten scenes: every shape kind, plus fuzzing/segment-multiplier/distance-limit); `test_a_figure_obstacle_reproduces_the_recorded_classic_golden_data` checks that an ordinary obstacle still reproduces it, so keep it. - **Terminology - "figure" vs "image":** the *figure* is the mathematical result of perfectly simulating the rules (like the Mandelbrot set); it can never be generated whole, and every picture the program makes is an *image* (a view) of it. What defines the figure: the termination limits, segment multiplier, fuzzing and the obstacles. Coloration, decorations and the Buddha blur only process or decorate generated data and are NOT part of it. Never call an obstacle or an exported picture "the figure" (the export choices are "Current image" / "New image"; the code says `render_current_image`, `has_image`).

The margin is half the image width, growing extra text columns when needed; its size depends only on the image size and the obstacle count (blocks have fixed heights), so all frames of a video match. Video frames resolve obstacle values per frame (`resolve_obstacles`). The Export designer's "Framing settings location: Left margin" adds the displayed framing's settings (`framing_info_block`: x, y, diagonal, aspect) to the same margin, below the figure's after a line of dashes (`FIGURE_INFO_SEPARATOR`; no line when the figure's settings are elsewhere - `left_margin_blocks`, `add_left_info_margin`); a block's height never depends on the numbers, so a video's frames still match. Its key is `framing_info_location`.

## Testing

`test_harness.load_module()` (called once by `tests/support.py`, plus by tests that need a fresh copy) stubs `tkinter`/`ttk`/dialogs with no-op widgets so the real program imports headlessly and its plain functions/classes can be tested. Each call imports the whole `lightbounces` package afresh and returns it (an independent copy; use it for tests that mutate module state); its modules are kept in `m.__lb_modules__`, not in `sys.modules` (tests that pickle use `_ModuleRegistered`, in `tests/support.py`). Names are READ through the package (`m.parse_dist_limit`), but a global is PATCHED or REBOUND in the module that owns it: `m.paths.EXPORT_DIR = ...`, `m.external.ffmpeg = ...`, `fresh.selfchecks.CAT_METRIC = ...` (rebinding it on the package would not reach the functions that read it; mutating an object in place, like `del fresh.DEFAULT_SETTING_VALUES[k]` or a class attribute, works anywhere). Anything needing a live Tk mainloop is out of scope and checked by hand. Bug fixes get a regression test whose docstring says what went wrong.

## Working preferences for this project

- After every edit: compile-check, then run the full test suite, not just
  tests that seem related.
- Flag risk and disagree with a plan when warranted, rather than silently
  complying or silently deviating. If a request has an unintended side
  effect, say so and explain the tradeoff before proceeding.
- Keep a visible, incrementing version counter in a long-lived file,
  updated on every delivery. This is `FILE_VERSION` in
  `lightbounces/version.py`: bump it by exactly 1 once per
  completed task/turn that changed the code, not per individual edit.
