# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

There is a git repo (the user commits between turns), no build step, no linter. Two source files matter: `light_bounces.py` (the whole app, ~8.6k lines) and `test_light_bounces.py` (+ `test_harness.py`).

```bash
python -m py_compile light_bounces.py      # compile-check
python test_light_bounces.py               # full suite (~8s); custom runner, not pytest
python light_bounces.py                    # launch the Tkinter app
```

- There is no single-test CLI flag. Tests are plain `test_*` functions (no args, raise `AssertionError`) discovered from module globals by `run_all()`. To run one: `python -c "import test_light_bounces as t; t.test_name()"`.
- Requirements: `numpy`, `numba` (without it everything runs in pure Python, unusably slow), `ffmpeg-python` + the `ffmpeg` binary for video, optionally `cjxl` for JPEG XL output.
- Baseline (verified on Windows, 2026-09-29): all 543 pass, none fail or skip, provided `cjxl` and `ffmpeg` are on PATH. Without the real `cjxl`/`ffmpeg`, `test_convert_apng_to_jxl_with_the_real_cjxl_produces_a_jxl_file` reports SKIP (not PASS); everything else still passes.
- cjxl tests are hermetic: `_PathContext` (in the test file) strips any real `cjxl` from PATH, then either leaves none (`_no_cjxl()`) or puts `dev/testing/` first (`_fake_cjxl(fail_on=...)`). The fakes there (`cjxl.cmd` for Windows, `cjxl` for POSIX) copy input to output, or fail if the input path contains `$FAKE_CJXL_FAIL_ON`. Keep the two fakes behaviorally identical.
- `convert_apng_to_jxl` runs the path from `shutil.which("cjxl")`, not the bare name, because on Windows a bare name won't launch `.cmd`/`.bat` shims.
- Source files use CRLF line endings, except `dev/testing/cjxl` (the POSIX fake), which must stay LF or its `#!/bin/bash` line breaks. When editing from a Python script, read and write in binary mode (or `newline=''`) so line endings aren't silently changed.
- Numba caches compiled kernels in `__pycache__` (`cache=True`); first run after editing a kernel is slow.

## Architecture

**Single-file Tkinter app.** `light_bounces.py` shoots a ray from every pixel inside any shape ("obstacle") whose "fire rays inside" is on. There is no separate bounding shape: the app starts with one obstacle (`default_starting_obstacle`: the unit circle, Reflect both ways, fires rays). At each shape edge a ray reflects, terminates or passes through, chosen separately for crossing in and crossing out; it also reflects off its own earlier path, and escapes if nothing is left to hit. Per-ray measurements are stored per pixel, so recoloring is instant without re-simulating. The module docstring (top of file) is the authoritative feature description; read it first.

Layout of the file, in order:
1. Constants/parameters, "Buddha" (density-scatter) blur kernels.
2. Data classes: `Keyframe`, `Shape` (the obstacle kinds are its subclasses `EllipseShape`, `RegularPolygonShape`, ...), `ViewConfig`, `RaySettings` (every simulation setting: the stopping limits, segment multiplier, fuzzing, Buddha blur, confinement and emission - the scene itself is obstacles and views), plus `SETTING_INFO`/`DEFAULT_SETTING_VALUES`/`SETTING_FLOAT_KEYS` registries, plus each shape kind's own `PARAMS` table.
3. Pure helpers: keyframe interpolation (`resolve_frame_settings`, `resolve_value`, `resolve_obstacle_arrays`, `resolve_views`), filename/settings text, parsers, hand-written PNG/QOI/JXL encoders and PNG decoder, image utils.
4. Geometry: shapes are built by `make_bound(shape, params)` into packed arrays (arcs+edges, or circles) that numba kernels can consume.
5. Coloration tables/metric catalogs, then `run_self_checks()` (called at import).
6. Numba kernels: `arcs_edges_hit`/`circles_*_hit` → `boundary_hit` (ray inside a shape) / `obstacle_hit` (ray outside it) → `trace_path` (one ray; every shape is an obstacle, passed as the `ObstacleArrays` bundle from `build_obstacle_arrays`) → `compute_stats`/`compute_points` → `render_rows(_wh)` and `scatter_multi_buddha` (parallel, row-banded).
7. `class App` (~4.4k lines, lines ~4200–8580): all UI, generation threads, timeline/keyframes, video render (`_render_worker`, `encode_video_output`).

Key design points that span multiple places:
- **Keyframes snapshot everything** needed to generate an image, independent of the live controls. Float settings are interpolated *linearly* between keyframes; non-numeric settings hold the earlier value. There are no per-keyframe interpolation methods and no keyframe thumbnails (both removed ahead of a planned keyframe overhaul; `Keyframe` is just `id`, `frame_index`, `data`). The obstacle-list and view-list thumbnails (`THUMB_SIZE`) are unrelated and stay. Dynamic lists (obstacles, views) use keys like `"obst:<id>:<field>"` / `"view:<id>:..."` so each list item's fields animate independently and list position never matters. Deleting an obstacle or view immediately purges its keys from every keyframe (`purge_keyframe_settings`); a render works from `snapshot_keyframes` copies so such edits can't leak into it.
- **Records of settings are strict dataclasses** (`strict_record`): `FuzzParams`, `BuddhaBlurSettings`, `RaySettings` (the one type for what used to be `Snapshot` and `Settings`: what the controls hold, what Revert restores, what Start compares, what a keyframe resolves to; the Buddha blur is `RaySettings.buddha_blur`), `KeyframeData` (`.settings`, `.outline`), `ViewSettings`, `ViewSnapshot`. They are frozen, `slots`, **keyword-only with every argument required** (no defaults, so a new field must be passed everywhere and a missing one is a TypeError), cannot be indexed, iterated or unpacked, and check every value against its annotation (int / float (an int is fine, a bool is not) / bool / str / tuple (a list is stored as a tuple) / a class) - so a type mistake fails at construction, naming the record and field. `r.replace(**changes)` makes a modified copy, `r.as_dict()` a shallow dict, and they pickle by field name (`__getstate__`; dataclass's own state for frozen slotted classes is a bare positional list). `ViewSnapshot` is a frozen copy of one live `ViewConfig`, for the background threads (new-image export, video render); its fields mirror the live class's `__slots__` (a test keeps them in step). An obstacle's frozen copy is a frozen `Shape` instead (see the obstacle paragraph). Attach a validator before `@dataclass` runs, or it is never called (`strict_record` does). `settings_of_current_image` gives the settings the image on screen was generated with - views are colored from those (Buddha coloration re-traces rays with the generated confinement and emission). **One table row per simulation setting** (`RAY_SETTING_SPECS`, a `RaySettingSpec` each: the path into a `RaySettings`, the control attribute, the widget the modified-outline surrounds, and how the control is written - `text`/`int_text`/`float_text`/`number`/`bool`/`choice`): `ray_settings_to_dict` / `ray_settings_from_dict` (used by `capture_all_settings` and `resolve_frame_settings`; int fields are rounded, bool fields made bool), `set_setting_control` (used by `load_value` and Revert, so there is one setter, not two), `SETTING_FLOAT_KEYS` (every float-typed field), `SETTING_WIDGET_ATTRS` and `DEFAULT_SETTING_VALUES` are all *derived* from the table and `DEFAULT_RAY_SETTINGS`. `run_self_checks` fails at import if a `RaySettings` field has no row (or a row has no field), so adding a setting means: the `RaySettings` field, its default, a `SETTING_INFO` row (label/tab), a `RAY_SETTING_SPECS` row, the control and its reading in `current_ray_settings`/`preview_settings`. `preview_settings` (hover/pinned ray previews: the generated settings once an image exists, else the controls using each entry's last valid value) and `current_ray_settings` (the controls' live parsed values, None while an entry is invalid; used by Start, the button states and keyframe capture) still build a `RaySettings` separately. What the image on screen was generated with is `generated_settings` (read through `settings_of_current_image`; the kernel-ready arrays `gen_fuzz`/`gen_confine`/`gen_emission` are made from it in `start`). A keyframe stores a view channel as a `ChannelSettings` record (`view_channel_value`), the keyframe settings list is built from `SettingEntry` records (`all_setting_entries`), and outlines from `ObstacleRing` records (`obstacle_ring_specs`); each setting's label and tab are in its spec row (`SETTING_INFO` is derived). **Kernel arguments are namedtuples, not records** (numba needs them, and cannot forbid indexing or positional construction): `FuzzRule`, `ConfineRule`, `EmissionRule` (built only by `fuzz_rule` / `confine_rule` / `emission_rule`) and `ObstacleArrays` (shapes, bounds, cx, cy, effects, fire_inside; built only by `build_obstacle_arrays`, from live shapes or frozen copies alike). In the kernels read them only as `rule.field` - a misspelled field is a compile error, and `test_kernels_read_their_rule_and_obstacle_arguments_by_field_name_never_by_number` scans the kernel sources for numeric indexing. (Verified: numba passes namedtuples through `prange` kernels and nested calls, caches them, and they are immutable inside kernels; a record *value* does not work inside `prange`, and a structured array still allows integer indexing.) The kernel signatures are now `trace_path(x0, y0, pts, kinds, max_iter, max_dist, seg_mult, fuzz, confine, emission, obstacles, raw)` and so on. Still positional: `Shape.params()` (a per-kind tuple, read only by the kind's `bound_from_params`), the registry row tuples (`ShapeParam`, `VIEW_FIELD_INFO`, `SETTING_INFO`), the packed `bound[...]` shape layouts (documented above `ellipse_bound`; 39 index reads), and `effects[..., 0/1]` (incoming/outgoing).
- **Parallel registries must stay in sync**, and `run_self_checks()` enforces this at import time (e.g. `SETTING_INFO` vs `DEFAULT_SETTING_VALUES`, each shape kind's `__slots__` vs its parameter tables, `KIND` matching its place in `SHAPE_CLASSES`, a field name meaning the same on every kind, per-`TERM_*` dicts, point-catalog lengths). When adding a setting, shape param, termination code, or metric, update every table; a self-check failure at import is the intended alarm. Tests deliberately break a fresh module copy to confirm each check fires.
- **Ray effects** (`OBSTACLE_EFFECT_REFLECT/TERMINATE/PASS`): `trace_path` tracks which shapes the ray is inside with a flag per shape, flipped by each pass-through crossing and never re-derived from geometry (except after a segment-multiplier pull-back). A crossing is not a bounce, records no point, and is part of one segment (`total_t`). A shape passing rays through both ways is skipped. `TERM_ESCAPED` rays end where they leave the [-1, 1] square (`square_exit_t`). Termination-reason metric values are evenly spaced 0..1 (`TERM_STAT_VALUE`); a new reason means rescaling them.
- **Obstacles are instances of `Shape` subclasses** (`EllipseShape`, `RegularPolygonShape`, `MossEggShape`, `CircularSectorShape`, `CircularSegmentShape`, `LensShape`, `ReuleauxPolygonShape`, `CapsuleShape`, and the arc loops `TrefoilShape`, `QuatrefoilShape`, `LuneShape`, `ArbelosShape`; `SHAPE_CLASSES` is indexed by `KIND`, the `SHAPE_*` code the kernels use, and `SHAPE_NAMES` is derived from each class's `NAME`). The kind is chosen when the obstacle is created - the Obstacles tab's `new...` menu button, `new_obstacle(shape_class)` - and never changes: there is no `shape` field or control, so keyframes cannot change it, and an obstacle has only the fields its kind needs. `Shape` holds what every kind has (`rotation`, the position `r`/`theta`/`cx`/`cy`, `in_effect`, `out_effect`, `fire_inside`); each subclass declares its own parameters once, as a `PARAMS` tuple of `ShapeParam` rows (field, label, default, animate, fmt, slider range) plus `__slots__` with the same names (a self-check keeps the two in step), and a `LAYOUT` (how its bound array is packed: `LAYOUT_ELLIPSE` / `_POLYGON` / `_CIRCLES` / `_ARCS_EDGES` / `_ARC_LOOPS`; the Python code that must treat packings differently, `offset_bound` and `ring_layer_masks`, branches on it, so a new kind that reuses a packing needs no edit there; the numba kernels `boundary_hit`, `obstacle_hit` and `inside_boundary` still branch on the kind's `KIND` code), and provides `params()` (the tuple its bound function takes), `bound_from_params`, `shape_text`, `extent`, `info_param_line` and, where the generic sampled edge is not exact, `boundary_xy`. `__init_subclass__` derives `NUMERIC_PARAMS`, `KEYFRAME_FIELDS` (field, label, is_float), `FIELD_NAMES` and `FIELD_TYPES`. A field type-checks on assignment (float: any real number but not a bool; int: whole numbers; bool: only a bool; an unknown field is an AttributeError). A *frozen copy* is the same class with every assignment refused: `snapshot()`, `with_values(**values)`; it is what the background threads read, what `gen_obstacle_snapshots` holds and what `resolve_obstacles` returns, and it has every method (describe, bound, center...). `duplicate(new_id)` makes a live copy of the same kind. Copy and pickle go through `__getstate__`/`__setstate__` (state `(None, {slot: value})`, what pickle gives any slotted object, so the dump viewer shows a shape as before). The editor builds one control group per kind from its `PARAMS` (`add_shape_param_row`, `obs_shape_groups`; `obs_widgets` is keyed `(Shape, field)` for a shared field and `(kind, field)` for a kind's own; read through `obstacle_widget`), shows the group of the selected obstacle's kind and its name (`obs_shape_label`). Keyframe keys are `obst:<id>:<field>` for the fields of that obstacle's own kind only, and its section of the keyframe list is titled by `obstacle_tab_title` ("Obstacle #2 (Lens)"). Every kind has the one `rotation` field but keeps its OWN zero orientation (polygon and Reuleaux vertex up, Moss egg pointed end up, ellipse width along x, sector/segment/lens/capsule along +x). `radius` is declared by polygon, Reuleaux, sector and segment (default `DEFAULT_RADIUS` = 1.0, range 0-2); polygon `sides` and `reuleaux_sides`, and the two spans, keep separate names on purpose (different ranges). Adding a kind: a subclass with `KIND`, `NAME`, `PARAMS`, `__slots__` and the methods above, its bound function and kernel support, a `SHAPE_*` code, a branch for it in those three kernels (unless a later change makes them dispatch on layout; the arc loops, kinds numbered from `SHAPE_FIRST_ARC_LOOP`, need none: `boundary_hit` and `obstacle_hit` fall through to `arcs_edges_hit`, and `inside_boundary` sends every code from `SHAPE_FIRST_ARC_LOOP` up to `inside_arcs_parity`), and an entry in `SHAPE_CLASSES` (the `new...` menu and everything else follow). **The arc loops** are concave shapes built from full circles by `region_arcs(circles, member)`: it cuts each circle where it crosses the others and keeps the pieces where the region is on one side only (identical circles are one; a quatrefoil at lobe size 1 would otherwise count its edge four times and break the even-odd test). `lobed_bound` (trefoil/quatrefoil: `radius` is the distance to the farthest point, `lobe_size` the lobe radius as a fraction of it, 0.52-1; below 0.5 the middle would be a hole), `lune_bound` (the outer circle `radius` about the origin minus a circle `cut_radius` whose centre is `cut_offset` away towards the rotation; degenerate cuts give a full disc, a disc with a hole, or nothing), `arbelos_bound` (`radius` and `split`, centred vertically on its bounding box, curved side up at rotation 0). Their outline is `chain_arcs_xy` (arcs joined end to end; a lune with a hole draws a joining line) and their ring layers use `arc_loop_distance`, because offsetting a concave arc outward would move it into the shape. A concave shape does not change the crossing cap in `trace_path`: a shape passes rays one way only, so a ray is passed through any one shape at most once per segment.
- **Angle controls are unlimited where the angle is a free quantity:** emission offset, fuzzing offsets, the obstacle rotation and theta take any number of degrees (`add_angle_entry` with no `lo`/`hi`), while a fuzzing jitter (a +/- range) keeps its 0-180 limits. The shape-defining angles keep the limits their geometry needs (Moss egg apex angle 60-180, circular sector span up to 180, circular segment span 1-359; `moss_egg_bound`/`make_bound` clamp them too).
- **Confinement** is a figure-defining setting (Simulation tab, `build_confinement_controls`): window size (2-999 path points), method (`CONFINE_BOX`: the window's bounding box is under the threshold in BOTH directions; `CONFINE_PATH`: the window's segments sum to under it) and one threshold in world units (any finite number > 0, never rounded or clamped - `parse_confine_threshold`; the key-press check is `validate_positive_float`). Defaults (4, Box, `PIXEL` = 2/512) are exactly the old hard-wired rule, guarded by the golden test. It reaches the kernels as a `ConfineRule` namedtuple (`confine_rule` / `settings_confine` / `CONFINE_DEFAULT`), right after `fuzz`. Keyframes: threshold interpolates, window and method hold. The rule is judged on the *recorded* path points, so with a segment multiplier below 1 those are the pulled-back points. Not built (declined): circle-radius detection, periodic-orbit detection. Note `TERM_CONFINED` is also (mis)used for a degenerate zero-length normal and the pass-through crossing safety cap; splitting them out would need a new termination reason (which re-spaces the termination metric).
- **Emission direction** is a figure-defining setting (Simulation tab, `build_emission_controls`): mode `EMIT_UP` (base direction 90 degrees) or `EMIT_TOWARDS` (from each ray's own start point to the target point; a ray starting exactly on it uses up), a target point positioned like an obstacle - four settings `emit_target_r` / `_theta` (degrees) / `_cx` / `_cy` (`EMIT_TARGET_FIELDS`; the point is `obstacle_center_from(r, theta, cx, cy)`, computed in `settings_emission`, so the kernels still receive x and y), each any finite number, `parse_target_coordinate`, never clamped, and an angle offset in degrees (positive = counterclockwise, *no limits* - any number of revolutions either way) ADDED to the base. Defaults (Up, target origin, offset -45) reproduce the old fixed up-and-right direction *bit-for-bit*: `unit_direction` returns exact vectors at multiples of 45 degrees. It reaches the kernels as an `EmissionRule` namedtuple (`emission_rule` / `settings_emission` / `EMISSION_DEFAULT`), right after `confine`. The offset applies in Towards mode too, so aiming exactly at the target needs offset 0. Fuzzing's old absolute "emission angle" was REMOVED (it replaced the direction whenever fuzzing was on, which would have defeated Towards); `FuzzParams` and the kernel's `FuzzRule` now have only `emit_jitter`, added on top of the emission direction. The ray preview follows the *generated* image's settings until Start is pressed again.
- **Testing the kernels:** `dev/testing/classic_boundary_golden.npz` is recorded output of the *old* fixed-bounding-shape implementation (ten scenes: every shape kind, plus fuzzing/segment-multiplier/distance-limit); `test_a_figure_obstacle_reproduces_the_recorded_classic_golden_data` checks that an ordinary obstacle still reproduces it, so keep it. Compiled kernels use their own RNG: seed it from compiled code (`_seed_kernel_rng`), not `np.random.seed`. Test scenes must start rays *inside* a firing shape (`_kernel_trace` puts a unit-circle figure first), or the ray correctly bounces off that shape's outside.
- **Terminology - "figure" vs "image":** the *figure* is the mathematical result of perfectly simulating the rules (like the Mandelbrot set); it can never be generated whole, and every picture the program makes is an *image* (a view) of it. What defines the figure: the stopping limits, segment multiplier, fuzzing and the obstacles. Coloration, decorations and the Buddha blur only process or decorate generated data and are NOT part of it. Never call an obstacle or an exported picture "the figure" (the export choices are "Current image" / "New image"; the code says `render_current_image`, `has_image`).
- **Figure settings margin:** the Export designer's "Figure settings location: Left margin" writes every figure-defining setting (`figure_info_blocks`: limits, segment, fuzzing, and each obstacle via `Shape.info_lines`) using lines of at most `FIGURE_INFO_COLUMN_CHARS`. The margin is half the image width, growing extra text columns when needed; its size depends only on the image size and the obstacle count (blocks have fixed heights), so all frames of a video match. Video frames resolve obstacle values per frame (`resolve_obstacles`).
- **Pixel font (`FONT_5X7`):** complete for A-Z, a-z, 0-9 plus `#`, theta and a few symbols (each glyph is 7 rows of 5 cells; `render_text_line` looks characters up strictly, so a missing one raises KeyError). The user has said new characters may be added to it whenever useful, without asking - add the glyph and a test. Known long-standing look-alikes: `o`/`0` and `x`/`\u00d7` share a picture.
- **Point dropdowns:** "Origin" and "Top left corner" are listed first (`POINT_MENU_LABELS`), but point ids never change (`POINT_LABELS.index(label)` still maps a label to its id).
- **Selecting a keyframe loads it; edits are marked "modified"** (`select_keyframe`, `apply_keyframe_settings`, `check_modified`): selecting loads every setting the keyframe defines plus every one its neighbors animate through it (`setting_status` "animated" = some other keyframe defines it, on either side: blended between the nearest on each side, or held from the first/last defining keyframe when only one side has one - `resolve_value`'s rules; settings no keyframe defines are left alone). Selecting another keyframe = deselecting first (`deselect_keyframe`: clicking the empty keyframe-list background, deleting the selected one, or selecting another); the controls keep their values but `kf_modified` is cleared. Modification is detected by *polling* `capture_all_settings` every `MODIFIED_POLL_MS` (`poll_modified`; ~0.06 ms per capture) and diffing against the previous capture (`detect_modified_keys`): any change marks a key, and it stays marked even if typed back, until saved or deselected. New keys (a just-added obstacle) are not edits; vanished keys are dropped. `kf_applying` suppresses checks while values are loaded. Blue outlines are `ModifiedOutline` frames placed behind each control (no layout changes), found via `SETTING_WIDGET_ATTRS` / `OBSTACLE_FIELD_WIDGET_ATTRS` / `SHAPE_PARAM_INFO` (self-checks keep these in step with `SETTING_INFO` / `OBST_FIELD_INFO`; a new setting needs its control attribute registered) and `chan_blocks` / `mode_combo` for views; obstacle and view outlines show only for the obstacle/view currently open in the editor. "Save all modified" (`save_modified_settings`) and per-setting Save clear those marks; there is no per-setting Load and no Load all. `new_keyframe` (from current) does not reload; `new_keyframe_empty` does.
- **Keyframe settings list sections are collapsible** (Timeline panel, `refresh_timeline_diffs`): each header (`diff_section_header_text`) toggles via `toggle_diff_section`; `App.diff_expanded` holds the expanded titles (empty = all collapsed by default, kept across rebuilds and keyframe selection). Every rebuild ends with `fit_diff_scroll` (the scroll area can't rely on the list frame's `<Configure>`: when the list shrinks below the scroll position the canvas shows none of it and never sends one, leaving a blank list). Collapsed sections build no rows, but Load all / Save all / Delete all still act on every setting. Obstacle/view sections are keyed by their "Obstacle #N" / "View N" title, so expansion follows list position. A "Show" filter above it (`diff_presence_var`: present / absent / present or absent, default all) narrows the rows via `setting_passes_presence_filter`; sections with no match are hidden, and the bulk buttons ignore the filter.
- **Pinned previews:** a pinned pixel keeps tracing its ray even where nothing fires (`update_preview`), and clicking it always unpins it (`on_click`); hovering a non-firing pixel shows nothing.
- **All output goes to `exports/`** (`EXPORT_DIR`, created on demand via `ensure_export_dir()`); video frames go in `exports/TEMP/` (`TEMP_DIR`). Tests must patch `m.EXPORT_DIR` / `m.TEMP_DIR` to a temp dir so nothing lands in the real folder.
- **Dump viewer (`dev/dump_viewer.py`, standalone dev tool):** `python dev/dump_viewer.py [dump.pkl]` (no argument: the newest file in `dev/dumps`) shows a dump as boxes (one per container/object, one row per entry, an arrow from a row to the box of its value; shared objects are one box with extra dashed-red arrows; stand-ins purple). It needs only tkinter (+ numpy if installed) and never imports `light_bounces` (classes from the app, `__main__`, `debug_dump` are read as `Placeholder` objects showing their attributes). **Model vs view:** `build_graph` makes every box once (`Graph`; each `Node`/`Row` carries a `type_key`, the type the filters act on: dict, list, int, `stand-in: <kind>`, a class name...); `apply_filters(graph, levels)` makes the `ViewGraph` of boxes that are visible (new `Node`s with the same ids, only the shown rows, `hidden` = entries removed by filters, drawn as a footer 'N children hidden by filters'); `Viewer.pos` keeps every box's position (hidden ones too) so filtering never moves anything and 'Rearrange' (`place_tree` on the view) only moves the visible ones. **Filter levels** per type, set in the left sidebar (constants `SHOW`=4 .. `LOWEST`=0, everything starts at 4): 4 show + children (each child still follows its own level), 3 show but hide children, 2 hide but keep a plain row in the parent, 1 hide and drop the row too, 0 (`LOWEST`) as 1 and also hides the *parent* box when every one of its entries is at 0 (`hides_itself`; needs at least one entry, the parent keeps its plain row in its own parent, no cascade further up, never the top box); the top box always shows its children; a type is listed once (a type with boxes, e.g. dict, is a box type even for its empty inline ones). **Layout** (`layout_tree` = `measure_nodes` + `span_tree` + `place_tree`) is a left-to-right spanning tree: each box's children are stacked in row order in a block beside it, starting `max(min_gap, aspect * span_h)` to the right of their parent (`span_h` = the vertical space all the children take up; so columns are per parent, not aligned by depth; the two values are the sidebar's Arrangement sliders 'Minimum horizontal spacing' (default 110) and 'Spacing aspect ratio' (default 0) and only take effect on Rearrange or opening a file), so boxes never overlap and the tree's own arrows never cross (tests check both on random nested data and after filtering; only extra arrows to shared/cyclic objects may cross). Real dumps come out ~2,800 wide and ~116,000 tall, so the start view is 0.8x around the top box, not fit-all; `F` fits all, `1` is actual size, `R`/the Rearrange button re-lays-out, View > Go to and clicking a link row navigate, **Scrolling and row order:** the plain wheel scrolls up/down and Shift+wheel sideways by `WHEEL_SCROLL_PX` (120) window pixels a click, Ctrl+wheel zooms at the pointer (`wheel` / `scroll_by`, which `on_pan` shares; Ctrl wins when Shift is also held; verified with real OS wheel input plus `keybd_event`). `make_view` = `apply_filters(graph, levels, unchecked, links_only)` then `arrange_rows(view, group_links, sort_by, descending)` (View > Group link rows first; View > Sort objects within their parent = none / name (`natural_key`: case-insensitive, numbers numerically) / size in bytes / total descendants / visible descendants, ascending or descending): rows that link to a *visible* box come first when grouping, then the sort applies inside each group, ties keep their order, the 'more entries' note stays last, and the view's edges are rebuilt for the new row indexes (so the children stack in the new order after a Rearrange). Sort keys live on `Row`: `size` (`deep_size`: an estimate of the memory the value and everything under it takes - arrays their `nbytes`, a large-array stand-in the size it records; each shared value measured once) and `desc_all` (`descendant_counts`: different boxes reachable below it, itself not counted, computed once at load over the whole graph with reachability bitsets in Tarjan order so cycles are fine; 'visible descendants' re-runs it over the view). The sidebar's 'Hide rows that aren't links' (`links_only`) drops every row that is not a link to a shown box - plain values, rows named for a filtered-out box, and rows cleared by their checkbox - and counts them in the box's 'N children hidden by filters' message; 'Show all' turns it off. **Back / forward history:** a link jump (`Viewer.navigate`: a click on a link row, or on a box's name) pushes the view it leaves (`current_view` = zoom, origin) on `back_stack` (capped at `HISTORY_LIMIT` 200) and clears `forward_stack`; `nav_back` / `nav_forward` (mouse side buttons, Alt+Left / Alt+Right, XF86Back / XF86Forward, View > Navigate back / forward with those hints, greyed out when empty via `update_nav_menu`) move between them and restore the exact view. View > Go to, Fit and Rearrange are not recorded; opening a file clears the history. **Side buttons (verified with real `SendInput` XBUTTON clicks on Tk 8.6.12 / Windows): back arrives as Tk button 4 and forward as 5** (`nav_button_numbers`; on X11 4/5 are the scroll wheel and the side buttons are 8/9, so the wheel-zoom bindings for 4/5 exist only on X11 - on Windows they would have made the side buttons zoom). **Link rows and checkboxes:** a row that points at a box is a link (underlined `Viewer.link` font, hand cursor): a click that is not a drag jumps to that box (`on_release` with `drag['link']`; `link_block_until` stops the second click of a double-click jumping again, and `on_double_click` only does the press's work). At the right of each such row is a checkbox (`Row.check`: None = no checkbox, True/False = ticked/cleared; `Row.origin` = (original box id, original row index)); `Viewer.unchecked` holds the cleared origins and `apply_filters(graph, levels, unchecked)` keeps a cleared row as a plain row (no arrow, not counted as hidden) without its box, so a box is visible only if its checkbox is ticked AND the filters allow it (a box also stays if another ticked row points at it). Plain-value rows get no checkbox (a hidden one could not be ticked again); boxes with checkboxes are `CHECK_W` wider; 'Show all' ticks everything again; the state resets when a file is opened. Zoomed in to `TWO_LINE_TITLE_ZOOM` (1.5) or more a box's title is two lines (the title bar is always `TITLE_H` = 34 world units tall, room for both): the name the box has in its tree parent (`name_in_parent`, from `parent_row`; underlined, clickable) above its type; clicking the name (`name_hit`) runs `go_to_row`, which centres that row of the parent and highlights it for 2 s (`flash`). View > Connections picks swoopy or straight arrows (`edge_path`: swoopy is a cubic Bezier sampled into 12-64 short segments so it is smooth all along, ends included, leaving and entering horizontally; lines are `EDGE_WIDTH` 2 with a larger arrowhead). The two filter lists in the sidebar fold (`section_open`). **Speed (measured, ~11k items): drawing everything and panning with `canvas.move('all')` cost ~120 ms per pan step and ~180 ms per zoom step; now only the boxes within the window plus a 30% margin are on the canvas (`nodes_in_region`, `visible_row_range`), a pan just moves those items (redrawing only when the window leaves the drawn region), and a zoom step recomputes the view origin and does one coalesced `redraw` (~17 ms at readable zoom, ~33 ms fitting everything; text is skipped below 5 px; each arrow is skipped when shorter than `MIN_ARROW_PX` (12 px) on the screen (`arrow_visible`), so zoomed far out only the long ones remain - at fit-all ~340 of 897 arrows are drawn, costing ~60 ms a redraw instead of ~33 ms with none; curves become straight below zoom 0.05). Painting wide lines is the main cost: a dashed line tens of thousands of px long (extra arrows to shared boxes) cost ~20 ms for six of them, so extra arrows are dashed only when shorter than `DASH_MAX_PX` (1500 px) and solid red otherwise; re-measure (`time redraw() + root.update()`) after changing line width, dash or point counts.** The view is `screen = (world - origin) * zoom`, not a canvas scale, so dragging a box edits its world position and moves only its few items. Mouse: wheel zooms at the pointer, right-drag pans, left-drag moves boxes or rubber-bands a selection (Ctrl adds), a plain background click deselects (the double-click handler also does the press's work: Tk sends a quick second press as a double-click *instead of* a press). The pure parts (loading, graph, filters, layout, region/row culling) are tested; the window was checked by hand with synthetic events.
- **The window is kept on screen at startup** (`keep_window_on_screen`, run 100 ms after the UI is built and again just before the startup screenshot): it only moves the window (never resizes it) by the smallest `shift_into_area` amount so its whole frame lies in the work area of its monitor (taskbar excluded; Windows asks the OS via ctypes in `window_rect_and_work_area`, other platforms use the client rectangle and whole screen). A window bigger than the screen is lined up by its top-left corner. The window is ~1920 px wide including its frame, so on a 1920-px screen only vertical moves show.
- **Debug aids (dev aids; all need the `dev/` folder, and never raise):** the Debug menu (`build_menu_bar`: Take screenshot / Dump (without large arrays) / Dump (with large arrays)) and, once per launch shortly after startup (`take_startup_captures`, scheduled at the end of `warm_up`), a screenshot then a dump. Screenshots go to `dev/screenshots/<FILE_VERSION>-YYYYMMDD-hhmmss-<startup|manual>.png` (Pillow's `ImageGrab`, real screen pixels, so anything covering the window appears; skipped without Pillow). Dumps go to `dev/dumps/<FILE_VERSION>-YYYYMMDD-hhmmss-<startup|crash|manual>.pkl` (`dump_app_state`; a same-second name gets `-2`, `-3`... via `unused_path`). Startup and crash dumps, and "Dump (without large arrays)" ones, replace every numpy array of at least 64 KiB (`LARGE_ARRAY_BYTES` in the dumper; purely by size, wherever it sits - the generated `stats`/`points`/`img`..., the `gx`/`gy` pixel grids, the hover buffers - so there is no list of attributes to maintain) with a stand-in recording its shape, dtype and size: a dump is then ~0.1 MB instead of ~52 MB. Crashes (an exception escaping a Tk callback via `on_callback_exception`, reaching `sys.excepthook`, or killing a thread) dump at most `MAX_CRASH_DUMPS` per launch, and never take a screenshot. The dumping itself lives only in `dev/debug_dump.py` (standalone; loaded by path at dump time): it knows nothing about the app's attributes, stores whatever pickles exactly as is, and replaces the rest with plain-dict stand-ins marked `__standin__` (Tk variables keep their value, widgets their options, unpicklable objects their attributes). Read a dump with `debug_dump.load_dump(path)`, which maps classes pickled as `__main__` (the program run as a script) to `light_bounces`. `dev/dumps/` is gitignored. Tests patch `m.DEV_DIR` (and `m.ImageGrab`) to a scratch dir.
- **The program never deletes files on its own.** The one exception is the Video panel's Clear button (`clear_temp_frames`), which, after confirmation, deletes only `frame_NNNNN.png` from `TEMP_DIR`. A video render refuses to start if `TEMP_DIR` is non-empty or two keyframes share a frame index.
- Output filenames derive from the script's own filename, so renaming the file changes them.

## Testing

`test_harness.load_module()` stubs `tkinter`/`ttk`/dialogs with no-op widgets so the real module imports headlessly and its plain functions/classes can be tested. Each call returns a fresh module object (use it for tests that mutate module state). Anything needing a live Tk mainloop is out of scope and checked by hand. Bug fixes get a regression test whose docstring says what went wrong.

## Working preferences for this project

- After every edit: compile-check, then run the full test suite, not just
  tests that seem related.
- Flag risk and disagree with a plan when warranted, rather than silently
  complying or silently deviating. If a request has an unintended side
  effect, say so and explain the tradeoff before proceeding.
- Keep a visible, incrementing version counter in a long-lived file,
  updated on every delivery. This is `FILE_VERSION` near the top of
  `light_bounces.py`: bump it by exactly 1 once per
  completed task/turn that changed the file, not per individual edit.
